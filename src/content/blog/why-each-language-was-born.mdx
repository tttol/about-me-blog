## Intro
AI時代に新しいプログラミング言語を学ぶ必要があるのか？
答えはYESです。

コーディング自体はAIに任せることができるようになりました。
だからと言って人間がプログラミング言語を学ばなくて良い理由にはならないと、自分は思います。
プログラミング言語が新しく生まれるということは、現存する言語では解決できない課題があって、それを解決するために開発されたということです。言語が誕生した背景と課題を知ることは、AIが台頭した現代においても学ぶに値する行為です。

ということで、本記事では私があまり詳しくない以下の言語にフォーカスして、誕生背景を調べていきます。

- Ruby on Rails
- Go
- Rust

## 2004: Ruby on Rails
Ruby on Railsは、Rubyで書かれたWebアプリケーションフレームワークです。David Heinemeier Hansson(DHH)がBasecampの開発で使った基盤を切り出し、2004年に初めて公開しました。
Ruby自体は、まつもとゆきひろ（Matz）が1993年に開発を始め、1995年に初めて公開しました。

コンセプトは`Convention over configuration`。つまり「設定よりも規約」。

ref: https://rubyonrails.org/doctrine#convention-over-configuration

Railsでは、命名規約に沿って書くと、アクションが使うビューテンプレートやモデルに対応するテーブルを個別に指定する手間が省けます。リクエストをどのアクションに渡すかは、ルーティングで明示します。

ノート一覧を表示する例では、まず `bin/rails generate` でコントローラーとビューのひな形を生成します。
```sh
# Generate the controller, index action, and view without adding a route.
bin/rails generate controller Notes index --skip-routes
```

```ruby
# config/routes.rb (keep any other existing routes inside this block)
Rails.application.routes.draw do
  resources :notes, only: [:index]
end

# app/controllers/notes_controller.rb
class NotesController < ApplicationController
  def index
    @notes = Note.order(id: :desc)
  end
end
```

`config/routes.rb` の `resources :notes, only: [:index]` は、`GET /notes` を `NotesController#index` に割り当てます。このアクションでは描画するテンプレートを明示していないため、Railsはコントローラー名とアクション名から `app/views/notes/index.html.erb` を選びます。生成されたテンプレートの中身を次のコードに置き換えます。

```erb
<h1>Notes</h1>

<ul>
  <% @notes.each do |note| %>
    <li>
      <h2><%= note.title %></h2>
      <p><%= note.body %></p>
    </li>
  <% end %>
</ul>
```

データベースの読み書きにはActive Recordを使います。Active Recordは、規約に従って単数形のモデル名 `Note` を複数形のテーブル名 `notes` に対応付けます。基本的な読み書きは、SQLを直接書かずにRubyのメソッドで行えます。

```sh
# Generate the Note model and a migration for the notes table, then apply it.
bin/rails generate model Note title:string body:text
bin/rails db:migrate

# Open the Rails console to run the Ruby examples below.
bin/rails console
```

マイグレーションを実行したら、別のターミナルで `bin/rails server` を起動し、ブラウザーで `http://localhost:3000/notes` を開くと一覧を確認できます。

テーブルとモデルクラスを用意したら、Railsコンソールで次のようにCRUD操作を試せます。
```ruby
# Create: new builds an unsaved record; save! persists it.
note = Note.new(title: "Learn Active Record", body: "Start with persistence.")
note.persisted? # => false
note.save!      # => true
note.persisted? # => true

# create! builds and saves a record in one step.
practice = Note.create!(title: "Practice note", body: "A disposable example.")

# Read: find one record by its ID or query multiple records.
Note.find(note.id)
results = Note.where(title: "Learn Active Record").order(id: :desc).limit(5)
puts results.to_sql # Show the generated SQL.
results.to_a        # Load the matching records into an array.

# Update: persist changes to an existing record.
note.update!(body: "Practice querying and updating records.") # => true
note.reload.body # => "Practice querying and updating records."

# Delete: remove the disposable record, running destroy callbacks.
practice.destroy!
practice.destroyed? # => true
```

## 2009: Go
2009年にGoogleが公開しました（設計が始まったのは2007年）。

開発者はRobert Griesemer、Rob Pike、Ken Thompsonの3人です。
きっかけはGoogle社内で使われていたC++への不満だったと言われていて、巨大なコードベースのビルドを待つ時間の合間に新しい言語の設計が始まった、という誕生秘話が知られています。

当時のGoogleが抱えていた課題はこんな感じでした。
- 大規模なC++コードのビルドが遅すぎる
- 依存関係の管理が複雑で、コードが読みにくくなる
- CPUがマルチコア化していく時代なのに、並行処理を書くのが難しい

Goのコンセプトは「シンプルさ」と「並行処理」。
言語仕様を意図的に小さく保ち、誰が書いても似たようなコードになることを目指しました。

Goでは並行処理を`goroutine`と`channel`という仕組みで実現しています。

以下は`goroutine`を使ったサンプルコードです。
```go
// Go Concurrency Explained: Go Routines & Channels
// https://youtu.be/B9uR2gLM80E?si=qbO3h96SEomUGt8B
package main

import (
	"fmt"
	"sync"
	"time"
)

func sleep(msg string, ch chan<- string, wg *sync.WaitGroup) {
	defer wg.Done()

	time.Sleep(1000 * time.Millisecond)
	ch <- fmt.Sprintf("This is the %s", msg);
}

func main() {
	startNow := time.Now()

	msgs := []string{"1st", "2nd", "3rd", "4th", "5th", "6th", "7th", "8th", "9th", "10th"}

	ch := make(chan string)
	var wg sync.WaitGroup

	for _, msg := range msgs {
		wg.Add(1)
		go sleep(msg, ch, &wg)
	}

	go func() {
		wg.Wait()
		close(ch)
	}()

	for result := range ch {
		fmt.Println(result)
	}

	fmt.Println("Duration:", time.Since(startNow))
}

```


```sh
❯ go run main.go
This is the 6th
This is the 8th
This is the 9th
This is the 10th
This is the 7th
This is the 5th
This is the 3rd
This is the 4th
This is the 2nd
This is the 1st
Duration: 1.000751917s
```

関数呼び出しの前に `go` を付けると、その関数を新しいgoroutineで実行できます。この例では、10個のgoroutineがそれぞれ約1秒待ちます。待機時間が重なるため、全体も約1秒で終わります。

Goランタイムのスケジューラは、G、M、Pを組み合わせてgoroutineを実行します。

ref: https://go.dev/src/runtime/HACKING

- G: goroutineそのもの
- M: OSスレッド
- P: MがGoのコードを実行するために必要なリソース。スケジューリングやメモリ割り当てに使う状態を持つ

例えば、あるジョブG1が発生するとM1とP1がG1のスケジューラによって割り当てられます↓

![gmp1](/images/gmp1.png)

G1がIO待ちなどで待ち状態に入った場合、M1はG1から切り離されて別のジョブG2に割り当てられ、G1の待ちの間にG2のジョブを進めます。このジョブの管理は全てGo内部のスケジューラが行います↓

## 2015: Rust
2015年に1.0がリリースされました（開発が始まったのは2006年）。

もともとはMozillaのエンジニアGraydon Hoareの個人プロジェクトでした。自宅アパートのエレベーターが故障して階段を登る羽目になり、その原因がソフトウェアのバグだったことに腹を立てたのが開発の動機だというエピソードがあるようです。2009年からはMozillaが公式に支援し、新しいブラウザエンジンServoの実装言語として育ちました。

Rustの設計目標の一つは、CやC++でシステムソフトウェアを書くときに起こり得る、次のような問題を防ぐことです。
- 解放済みメモリへのアクセス（use after free）
- バッファオーバーフロー
- 複数スレッドでのデータ競合

大規模ソフトウェアの深刻な脆弱性の多くは、このメモリまわりのバグが原因だと言われています。C/C++は高速な反面、メモリ管理をプログラマの注意力に頼っていて、ミスがそのまま脆弱性になっていました。

コンセプトは`Ownership`（所有権）。
Rustでは、値を誰が所有し、どこから借用できるかをコンパイラがチェックします。例えば、所有権を手放した変数から、その値を読み出すことはできません。

```rust
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // 所有権がs1からs2へ移動する（move）
    // println!("{s1}"); // s1はもう使えないのでコンパイルエラーになる
    println!("{s2}");
}
```


これは他の言語にはない中々特殊な仕様です。
s1を`get(s1)`のように何かしらのメソッドの引数に使った時も同様に所有権がメソッド側に移るため、`println!(s1)`はコンパイルエラーになります。
Rustを自身の手で書いてみると、コンパイルが中々通らないなと感じると思います。それくらいmemory safetyに関する仕様がガチガチです。

これだけ聞くとなんだか書きづらい言語だなあと感じるかもしれません。しかしメリットもいくつか存在します。

まずはメモリセーフであること。
Cのように悪い意味で自由なメモリ管理ができる言語ではプログラマの不注意によってメモリリークが発生するリスクが拭えません。Rustでは逆にガチガチなメモリセーフをコンパイル時点で要求してくるため、基本的にメモリリークは発生し得ません。

また、所有権の移り変わりがコンパイル完了時点でわかっているためヒープ領域の管理もGCに頼らずに所有権に移り変わりに沿って管理すればよく、その結果高速な処理が実現可能です。先程のs1, s2の例でいうと、`let s2 = s1;`が実行された時点でs1はもう所有権が委譲されこのプログラム上では他から一切参照されないことがわかります。


## おわりに
こういう歴史的な背景もAIに聞けばすぐにわかるようになりました。本当にいい時代です。（ファクトチェックの手間はありますが）
AI台頭以前は、自分の手でコードを書くために言語そのものを勉強に文法やフレームワークを学ぶことが主流でしたが、AIがコードを書いてくれる現代では学びの方向性を変える必要があります。何かアプリを作る時は「どの言語・フレームワークを採用するか」の部分に人間が力点を置き、それぞれの言語が強みとしている部分を歴史的背景から理解し、技術選定に臨む必要がありそうです。
